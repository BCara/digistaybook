Verify the complete local journey

  • Host review: approve one [review] memory and confirm it appears on the public wall. Choose Keep off wall for another and confirm it stays hidden.
  • Review switch: turn it on, submit a new clear memory, and confirm it waits. Turning it off does not publish items already waiting; approve them individually.
  • Admin: sign in as operations@example.test, using the same local password. Choose Safety cases → Open case. Release one memory to the host, then approve it as the host. Delete a separate test case and confirm the wall has no visible post.
  • Photos: attach an ordinary authorised photo to a [safety] memory; open it using the admin case's photo button. This tests photo access and review controls, not image classification.
  • Recovery: edit your own outage memory in the same guest browser to remove [outage]. Check the new revision follows the clear route. Seeded posts belong to a different guest session.

Local operations access simulates the reviewer MFA requirement. The launcher runs local workers periodically; npm run test:local:workers runs due work, without bypassing backoff or deletion deadlines. Local tests do not emit the real provider score events.

Submit a live test and inspect its results

Use the existing owner-authorised test property, My Property Name, reference chpLFZnSbGBPpoPRNBlb. General public intake remains closed in the recorded configuration. The configured exception ends at midnight at the end of 9 October 2026, Sydney time.   1. Sign in to the live host dashboard. Open the property's in-stay guest link or QR link in a private browser window. A plain public wall link cannot submit a memory.
  2. Submit a uniquely labelled example, such as SCREEN-01 Lovely stay and a beautiful garden. Record the time. For photos, use an ordinary authorised garden or room image. To reproduce the profanity concern, use a synthetic example such as SCREEN-02 Fuck you and record the expected result as host review.
  3. In Firestore, open guestSubmissions. Locate the record by propertyId, time and test label. Copy screeningReference, and record the document ID and revision. Delivered or held private feedback is moved out of the submission's raw text field, so find feedback records by property, time and kind.
  4. Open Logs Explorer with a Google account that has project log access. Set the time range to cover your test, paste the focused query below and run it.
  5. Expand each entry's jsonPayload. Read the provider scores, the app's decision and the final state. Compare those with the actual guest wall or private inbox.

DigiStayBook admin permission and Google Cloud console permission are separate. One does not automatically grant the other.

resource.type="cloud_run_revision"

jsonPayload.event=~"^screening_(text_result|photo_result|provider_decision|memory_decision|feedback_decision|final_state|error)$"

Use timestamps to find your test, then narrow to its reference. Logs deliberately exclude guest text and photo bytes.

EventWhat it tells you
screening_text_resultcategories contains Google's category names and confidence scores from 0 to 1. Text uses the Australia endpoint.
screening_photo_resultOne entry for each successfully scanned photo. photoIndex starts at 0. categories contains adult, violence, racy, medical and spoof likelihoods. Photo scanning uses the EU endpoint.
screening_provider_decisionThe combined text/photo result: clear, standard or critical, with flags and thresholds.
screening_memory_decisionThe app's memory decision after its contact/link check. contactDetailsOrLinkHold: true means that check added host review to a provider-clear result.
screening_final_statefinalStatus is the committed publication/review status for that attempt. A clear screening result can still end as standard because host review is on. state_changed_no_publication means that attempt did not commit publication.
screening_feedback_decisionPrivate feedback verdict: deliver or critical. Feedback never publishes on the wall. Confirm actual delivery/holding in the stored record.
screening_errorA sanitised reason such as provider_timeout, provider_http_403, invalid_provider_response or daily_capacity_exhausted. Memories remain private; feedback remains undelivered.

Check the current revision. Editing a memory gives it a new screening reference. Retries of the same revision share a reference; distinguish them by timestamp. A provider score is not an accuracy percentage, and a “clear” scan alone does not prove publication.

04 · Property owner

Review memories and private feedback as the host

  1. Open your property → Moderation → Guest safety review. Press Refresh.
  2. Awaiting safety screening: the check has not completed. Content remains private, and the host cannot approve it yet.
  3. Ready for host review: read the message and use View … photos if present. Choose Approve memory to publish, or Keep off wall to leave it hidden. Refresh the guest wall to confirm the result.
  4. For private messages, open the property's Private feedback page. Ordinary complaints, including rude or profane ones, can reach this inbox after screening. If a message needs safety review, use Report message; it leaves the inbox while operations reviews it.

Review content before publication holds even clear new memories for approval. It does not retrospectively hide published posts, and turning it off does not approve the existing queue.

The queue is restricted to the owning host. An admin account does not automatically gain another host's approval controls. A serious safety case cannot be approved here. “All clear” describes this host queue; it does not establish that every submission passed every check.

05 · Operations admin

Open and resolve restricted safety cases

Live admin operationsLocal admin operations
  1. Sign in to /operations. Live access requires an account with the admin: true claim and a sign-in completed with a second factor. The local operations test account uses a simulation.
  2. Change Queue to Safety cases. Press Refresh queue. Use Load more cases if your case is not on the first page.
  3. Find the case reference and press Open case. Read the message and the displayed flag categories. For a memory with photos, press View … case photos. Opening a message or photo is audited.
  4. Add a short Decision note explaining the action. Keep the note about the decision rather than copying the guest's text.
  5. Select the appropriate action below, then refresh the destination to verify it.
Admin actionGuest memoryPrivate feedback
Release to hostRemoves the safety hold and sends the unchanged revision to host review. It does not publish. If the guest edited the memory while held, the current revision returns for fresh screening.Delivers the message to the property's private host inbox.

A guest-withdrawn memory cannot be released. Its existing safety hold can be resolved by deletion. Case photos are unavailable after release or deletion.

This is not an “all screening results” dashboard. Safety cases show serious automated flags and host-reported feedback. Clear or ordinary host-review submissions do not appear here. Detailed scores for any real scan must be checked in Logs Explorer.

For repeated screening failure, select the Alerts queue. For a deleted memory, select Deletion jobs and inspect its record/status using the appropriate data console. The operations overview currently lists these records; it does not provide a general retry or deletion-job execution button.

These thresholds are provisional engineering rules, not calibrated accuracy guarantees. Short insults can miss the threshold; benign context can also be flagged. Check actual scores and log a mismatch. No automatic rejection or reporting to authorities is performed by this screening route.

Confirm the stored state

In guestSubmissions, status: published means published; standard means host review; pending means incomplete screening; critical with safetyCaseOpen: true means restricted safety review. rejected means the host chose Keep off wall. For feedback, inspect feedbackStatus: delivered / held; pending screening may have no feedbackStatus and screeningFeedbackPending: true. Also inspect the current public post's visibility and the actual wall; a later report, edit or deletion can change visibility after screening.

07 · Resolve a confusing result

Common checks

What you seeWhat to check next
An obvious insult publishes locally.The local default is clear. Use [review] to test routing. Run a real provider test to assess classification.
An insult publishes live.Find the current revision's scores and final state. Check the 0.8 threshold, host-review setting and whether a host approved it. Record a missed expected hold; the screenshot alone cannot identify the cause.
No admin safety case exists.The item may be clear, ordinary host review, still pending or already resolved. Check Firestore and logs. Admin Safety cases is only one destination.
Admin access is denied.Confirm the app account's admin claim and second-factor sign-in. Google Cloud ownership alone is insufficient. Ask the project owner to verify provisioning rather than weakening the access check.
The host sees Ready for host review despite clear scores.Check the review switch and contact/link rule. Review does not always mean Google flagged the content.
No logs match.Confirm production project, time range and current screening reference. Local simulated scans do not create real text/photo score events. An incomplete upload may not have started screening.
A submission stays pending.Look for screening_error, screeningBudgetWaiting, retry fields and Alerts. Incomplete scans must remain private.
Daily capacity is exhausted.Read screeningDailyUsage/YYYY-MM-DD for the Sydney date. The app shares 100 attempts/day and warns at 75. Edits, failures and retries consume attempts; a memory with multiple photos reserves one attempt. Wait for capacity after midnight; do not bypass the counter.
There is a warning or notification record.Check actual email receipt separately. A queued notification or configured alert is not evidence that someone received it.
08 · Keep evidence

Record expected and actual results

For each case, record environment, label, property, time, submission ID, revision, screening reference, provider scores, expected destination, actual destination, reviewer and any decision. Mark unexecuted cases NOT RUN. This page is a guide; it does not fetch results or save a shared test ledger.

Keep routing results and classification results separate. A local marker verifies a route. Real provider scores reveal what Google returned. The final stored state and destination show what DigiStayBook did with that result.
