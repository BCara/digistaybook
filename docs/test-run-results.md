## Critical caveat — read before trusting any single row below

Two things happened during this run that materially affect how much weight to put on individual results:

1. **The codebase was being actively edited by another process during the entire Part C run.** `git status` repeatedly showed files flipping between `M`/`D`/untracked while I was testing (e.g. `src/styles.css` was briefly *deleted* at 10:05:33, causing a genuine transient blank-page/404 state; `src/ui/pages/LandingPage.tsx` was also briefly deleted later). By the end of the session the landing page's hero content had changed from "Turn every stay into a story worth keeping." (verified in C.1) to "Every guest signs the same book." with what looked like duplicated "GUEST BOOK"/"GUEST WALL" mockup sections — a state I did not formally test against the strategy doc's C.1 assertions because C.1 had already been completed against the earlier, stable content. **Every result below is stamped to the state observed at the time it was checked; the current HEAD working tree is almost certainly different again by the time this is read.**
2. **Real mouse/keyboard input delivery into the Browser pane was not working in this session.** Both `computer{action:"screenshot"}` and real `left_click`/`type`/`key` interactions failed to produce visible effects (clicks did not move `document.activeElement`; a `Tab` keypress did not move focus off `<body>`), while the error message on the screenshot call stated explicitly: *"the Browser pane is not displayed, so the page is not compositing frames."* This looks like an environment limitation of running as a subagent without a live-displayed pane, not an application bug. I confirmed the coordinate math was correct (`document.elementFromPoint` matched the intended element) but no focus/typing effect followed a `computer` click. **Workaround used:** for every interactive check (form submission, checkbox, menu toggle, disabled-button click-through), I dispatched real native DOM events via `javascript_tool` (`element.click()`, native-setter + `input` event, etc.) instead of the `computer` tool. This still exercises the real React event handlers (not a mock), but it is not literally the same as an OS-level mouse click, so I am flagging it rather than silently presenting it as identical to the strategy doc's exact method.
3. Consequently, the two required **screenshots** (C.2, C.11 request) could not be captured — this is recorded as **BLOCKED**, not skipped.

## Notable observations

- **Concurrent live editing of the working tree during the test run.** This is the single most important thing to flag. Starting mid-way through C.3 (~10:03–10:08), `git status` showed continuous churn in `src/styles.css`, `src/ui/pages/{Landing,GuestWall,StayWall}Page.tsx`, `src/ui/wall/MemoryWall.tsx`, and others, including `src/styles.css` being fully **deleted** for roughly two minutes (10:05:33–10:07:56) and `src/ui/pages/LandingPage.tsx` also being deleted later in the session. Vite's dev-server log recorded dozens of `hmr update` events and at least two `Pre-transform error: ... Does the file exist?` failures during this window. During the deleted-file window, `/stay/demo-cottage` genuinely rendered blank with real 404s in the console — a transient, environment-caused failure, not a code defect (I did not touch these files). By the end of the session the landing page's hero copy had changed from "Turn every stay into a story worth keeping." (as tested and passed in C.1) to "Every guest signs the same book." with an apparent duplicated "GUEST BOOK"/"GUEST WALL" mockup section. **Whoever owns this branch should know another process was actively committing/editing to it during this test session** — the branch name (`codex/implementation-foundation`) and the recent commit "docs: establish autonomous implementation checkpoint" suggest an autonomous implementation loop may be running against this same working tree concurrently.
- **Dev server port mismatch.** `.claude/launch.json` (pre-existing, not created by me) configures port `5173`, but ports 5173, 5174 and 5175 were already occupied by other processes when the dev server started, so Vite bound to **5176** instead. The `preview_start` tool's own proxy (port 58331, auto-assigned) never successfully connected — `navigate` to it returned `ERR_CONNECTION_REFUSED`/`ERR_ABORTED` every time. I navigated directly to `http://localhost:5176` for the entire Part C run, which worked reliably. Anyone re-running this suite should check for stray processes already bound to 5173–5175 before starting.
- **Oversized memory-card images observed once.** During one check on `/stay/demo-cottage` (mid-session, coinciding with the concurrent CSS edits), the 8 memory-card images rendered at 397×663px each (portrait, `object-fit` seemingly not constraining height), pushing `document.documentElement.scrollHeight` to 6153px. This may well have been a transient artifact of the concurrent `styles.css` edits rather than the file's settled state — flagging for awareness rather than as a confirmed defect, since I could not re-isolate it as stable/reproducible against a quiescent tree.
- **B.4 bundle size is modestly above the recorded baseline**: 283.92 kB raw / 86.33 kB gzip vs. the ~260 kB / ~79 kB baseline noted in `docs/implementation-status.md` (~9% growth both ways). Not a failure per the strategy doc's own framing, but worth tracking.
- **C.4/C.5 character counter correctly reflects real typed input** (1200 → 1175 after a 25-character message) when driven through native `input` events — confirms the counter is wired to live component state, not a static string.
- Console messages accumulated in the tab's history across navigations and were not always cleanly scoped to the current page load (some stale errors from the 10:05:33 transient-deletion incident kept reappearing in `read_console_messages` output on later, unrelated routes). I cross-checked with fresh `read_network_requests` calls each time to confirm the *current* page state was actually healthy (all 200s) rather than trusting console history alone.
