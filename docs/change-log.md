# Change log

## 2026-09-15

- Stopped re-buying the price list on every look. Opening the activation screen called Stripe twice from Sydney — one retrieve per plan — and did it again on every reopen and every change of country, to check two Prices against figures that are compiled into the service. The retrieve is not where the number comes from: it is the guard that stops the catalogue drifting away from the published rate (BOP §4.3). A quote that passes that check is now remembered for five minutes per instance, and the commitment path does not read it — `createActivationCheckout` always confirms the catalogue live, because the moment a card is about to be charged is the moment drift matters (D-025).
- Asked for the property and the host record together. `activationOptions` read the property, then read the host document to see whether the trial was still available; the second does not depend on the first — it is keyed by the uid on the request — so they are now asked for at once, and a caller who does not own the property is still refused on the property.

## 2026-09-14

- Put the house guidance back on the wall it was written for. `publicProperty` gated the whole arrival note and every essential behind `profile.publishHouseInformation`, a flag that defaulted to `false` — so a Host who filled in the Wi-Fi, the checkout time and the bins, watched all three appear on the canvas and in the phone beside it, and then opened the wall behind their own QR display, was met with "No house essentials. Wi-Fi, checkout and the bins go here." The flag is gone, along with its checkbox. There was already a gate, and it is the right one: the in-stay wall is reachable only with the token minted into the placard (D-012), and `resolveWallView` turns a caller without it back to the public wall before any of this is projected. A second, default-closed switch on top of that did not add privacy, it subtracted the feature — and it disagreed with `stayNoteOff` and `factsOff`, the two controls a Host actually meets, which take the note and the essentials off the wall and keep the words. The public wall still carries none of it, in either direction (D-013).
- Stopped the in-stay wall opening with the public wall's header. It rendered the location, the name and then `profile.welcome` — the sentence written for a stranger following a shared link — above the house information, which is why a bare property read "No welcome note. This is the first thing a guest reads." on the one wall where it is not. A guest reaches this wall by scanning the placard in the hallway: they have already let themselves in, and the first thing they are asking is whether they scanned the right display. So it now opens the way the demo wall and the property canvas both draw it — cover, the property's name at the size that answers the question, the place — and then the hosts speak, in the arrival note, over the essentials. `StayWallHeader` in `src/ui/pages/LiveWallPage.tsx` is that arrangement; the public wall keeps the header it had.
- Sent the preview checklist to the field that would fix it. `wallGaps` asked every wall for a welcome, so a blank in-stay wall told a Host to "Write a welcome" and pointed them at a line that wall does not carry. On the in-stay wall the gap is the arrival note, and it is named as one.
- Signed the public wall with initials when there is no portrait. The byline was inside `{hostPhoto && …}`, so a property with "Ana & Tom" typed in and no photograph uploaded lost the names along with the picture — while the canvas, the phone and the hosts' own notes all fall back to initials.
- Gave the essentials something to aim at. The four or five lines a guest hunts for with a suitcase still in their hand were four short words in the same uppercase, so finding the Wi-Fi meant reading the grid rather than seeing it. Each line now carries a drawn mark — `src/ui/wall/EssentialMark.tsx`, on the property column's grid and stroke weight — on the in-stay wall, the demo wall, the phone preview and the canvas, where it changes as the label is typed and tells a Host their word was recognised. The mark is read off the words a Host already wrote ("Bins", "Rubbish", "Bin day" are one mark) rather than picked from a list: an essentials line must not become one more thing to configure, and a label nothing matches gets the neutral mark instead of a wrong one. It is decoration and is hidden from assistive technology, which reads the label as before.
- Stopped a guest waiting on a token nothing checks. Opening a wall took 2.24s to get its content on the deployed site with a warm cache and a warm function, and about 1.1s of that was reCAPTCHA Enterprise: the callable SDK holds a request until App Check has a token, and the default app attests because every *other* endpoint refuses a call without one. `getPublicWall` is the exception — it is the single callable declared without `enforceAppCheck`, and the token it was given was discarded on arrival. The read now goes through an app of its own with no attestation and no Auth, so it leaves the browser as soon as the SDK has parsed rather than after a round trip to Google; a signed-in Host still reads through the default app, because the owner preview of a closed wall is resolved from the uid on the request (D-024). The same measurement is now 0.75s, and the attestation happens afterwards, where the contribution form will want it.
- Started the connection to Sydney while the page is still drawing. The wall read cannot be issued until React has mounted, so the DNS lookup and TLS handshake for the callable region are begun from the entry module instead of at the moment of the call.
- Kept the guest's wall warm. `getPublicWall` had no `minInstances`, so the first person to scan a placard after a quiet spell waited for a Node container to start in Sydney — two to five seconds in front of someone standing in a doorway with a suitcase, on top of everything else. It now holds one resident instance. Every other callable stays cold on purpose: they are all reached after a deliberate act, inside a click that already expects to take a moment.
- Took a round trip out of the wall read. The handler read the property, queried the posts, then read the property a second time to catch a wall suspended in between. The second read now runs alongside the posts query rather than after it. That narrows the window the recheck covers by the length of that query; neither ordering was ever airtight — a suspension committed after the read still lands after the response — and the next request is what closes it in both.

## 2026-09-10

- Built the cancellation the acknowledgement had already promised (ST-09). Every Host who activates a property ticks a box against a sentence ending "You can cancel at any time in your Host Dashboard with one click", and the Host Dashboard said, in its own fine print, that cancelling was not built yet. `cancelSubscription` sets `cancel_at_period_end` on Stripe's copy of the subscription and nothing else — it does not write `lifecycle` or `serviceEndsAt`, because `customer.subscription.updated` is already handled and `stripeBilling.resolveLifecycle` already maps a cancelled-but-running subscription to `cancelled_pending_end`. Writing the state here as well would give a property two authors that disagree the moment Stripe refuses the update. The date the confirmation shows comes from Stripe's answer to the write, not from the property document, which the webhook may not have caught up with yet.
- Made cancelling reversible while there is still something to reverse. `cancel_at_period_end` is a flag, not a deletion, so `resumeSubscription` clears it: same wall address, same placards, no new checkout, no second trial. Without it a mis-click costs a Host their property until they buy it back, and §4.1 would not give them the trial again.
- Stopped the billing screen reporting a payment that never happened. Stripe raises a zero-amount invoice when a trial starts and marks it paid, and the webhook stamped `billing.lastPaymentAt` on any `invoice.paid` — so a Host on day one of a free trial, whose card had never been charged, was shown "Last payment: 10 September 2026". `paidAtOf` now requires `amount_paid > 0`, and takes the invoice's own `paid_at` rather than the clock, because a webhook replayed a day late must not restamp the payment as today.
- Answered the question the billing screen was built around and had never asked. It showed three dates — "Trial ends", "Current period ends", "Last payment" — and left the Host to work out which of them was a bill. During a trial the first two are the same date, because the trial *is* the current period, and the third was the invented payment above; so the page printed three dates and stated the only one that costs money nowhere. It now opens on that sentence — "Your card will be charged A$15.00 on 8 October 2026" — and the date rows below it are omitted rather than duplicated or filled with "Not set".
- Taught the webhook what the next charge will be, so the screen can say it rather than imply it. `billing.renewalAmount` / `renewalCurrency` / `renewalInterval` come off the subscription's price, read through `currency_options` when the subscription is billed in something other than the price's base currency — otherwise a US host on a USD subscription would have been quoted the Australian figure. The expand that makes `currency_options` available is wrapped: a rejected expand path would throw inside the handler, and a throw there is a 500 Stripe retries, so a failure falls back to the plain read and the screen shows the date without a figure.

## 2026-09-09

- Moved the promotion code off Stripe's page and in front of it (ST-D13). §4.1 has always required a 100% code to be able to activate a property without taking a real payment, and `allow_promotion_codes` did that — on Stripe's screen, which is *after* the acknowledgement. A Host ticked a box reading "I understand I will be billed A$15.00 on 7 October" and then watched the total become A$0.00 somewhere we do not control. The activation screen now has its own field: the code is resolved against Stripe, and the whole quote is re-quoted around what the card is actually charged. A code that does not exist, has expired, is denominated in another currency, is restricted to products we are not selling, or does not reach either plan's price is refused **here**, in a sentence a Host can act on, with nothing quoted and nothing charged.
- Re-quoted the §6.3.4 terms rather than annotating them, because the sentences state the amount and a code makes the amount wrong. `billingPolicy.ts` gains a discounted disclosure and mints policy version `handbook-6.3.4-v2`; the undiscounted sentences are byte-for-byte what v1 said. The acknowledgement needed no new wording at all — it was never about the rate card, it is about the charge, so it is the same sentence with the discounted price in it. The renewal clause follows the coupon's own `duration`: a `forever` code renews at the discounted price, a `once` code renews at the published one, and a `repeating` code says how many months it lasts. That is the sentence that decides whether a Host is surprised by their second invoice.
- Sent Stripe one of the two, because Stripe will not take both. `discounts` and `allow_promotion_codes` are mutually exclusive on a Checkout Session, so a code resolved in our screen replaces Stripe's field rather than joining it — and a Host who typed nothing still meets that field, unchanged. The field itself is collapsed behind "Have a promotion code?", which is how Stripe presents its own and what the plan's "not marketed" note asks for: an always-open box on the last screen before payment advertises a discount to every Host paying full price.
- Kept the amount honest across the two calls. The commitment re-resolves the code instead of trusting the quote, and refuses a charge the Host did not acknowledge — the same guard, and the same remedy, as the trial date beside it. A coupon deactivated or halved while the terms were being read now stops the purchase rather than quietly selling at a different number. The acknowledgement record keeps both the published rate and the discounted charge, plus the code and its Stripe id, because the evidence is the offer and not just the total.
- Stopped telling Australian Hosts they are billed in the United States. `detectBillingCountry` read the browser's declared language regions first and the clock only as a fallback, on the reasoning that a language is a setting a person chose while a time zone can be a factory default. That is true of the time zone and exactly wrong about the language: `en-US` **is** the factory default — Chrome ships it, Windows ships it, and neither changes because a machine is switched on in Sydney. So a Host in Australia opened the activation screen reading "Billed in United States", was quoted US$10 instead of A$15, and was asked to tick a box against a price in the wrong dollar. The clock leads now, because it is the signal nothing defaults *to*: `Australia/Sydney` is not a value a laptop arrives with. Language still decides when the clock names nothing we serve, so a Host on `Etc/UTC` reading in `en-AU` is still found, and a US Host reading in `en-GB` was only ever found by the clock anyway.
- Put the two plans side by side and the terms underneath, once. The activation screen stacked them as two radio rows, each carrying its own seventy-word §6.3.4 disclosure — which set the one thing a Host is choosing between, fifteen dollars a month or a hundred and fifty a year, in the same typographic weight as two near-identical paragraphs of law, and asked them to find the difference by reading both. The prices are now columns sharing one hairline, the same arrangement `/pricing` already uses for the same two numbers, with the annual saving derived from the published rate card rather than typed. The disclosure and its checkbox appear once, below, for the plan actually chosen — the only plan it describes, and the only point §6.3.4 requires it to be read. Until a plan is picked, that space says so rather than sitting empty beside a disabled button.
- Named the plan radios rather than letting the card name them. A wrapping label names a control by concatenating everything inside it, and the accessible-name algorithm puts no spaces at the element boundaries this layout is built from — "MonthlyA$15.00per monthBilled every month." Each radio carries its own `aria-label` (the plan, the price, the period, which is the choice being made) and points `aria-describedby` at the note under it, which includes the "Two months free" badge in words because a badge beside a heading is a visual adjacency a screen reader does not get.
- Stopped Stripe contradicting our own trial length. Every page we write says "28-day free trial"; the Checkout page it hands a Host to said **27 days free**. Nothing was wrong with the date — both agreed the trial ended 7 October — but `trialEndFor` set the end to the instant exactly 28 days from the moment the quote was issued, and Checkout renders the trial as whole days remaining, floored, when the payment page loads. The minutes a Host spends reading the disclosure and ticking the box are therefore always subtracted from the twenty-eighth day, and the last screen before a card is entered undercuts the offer that got them there. The trial end now lands on the first **12:00 UTC at least 28 days out**, so the remaining trial is always in [28, 29) days however long that gap is, and Checkout floors it to 28. A trial can run a few hours past 28 days; it can no longer run under.
- Midday rather than the end of the day because the date is printed twice, in two timezones. The §6.3.4 disclosure and the acknowledgement are built from UTC components, while the Host Dashboard renders the same instant in the browser's own timezone — and 23:59 UTC reads as the next day for every Australian Host, which would have traded a wrong day count for a wrong date on the one line a Host ticks a box against. 12:00 UTC is the same calendar date from UTC-11 to UTC+11, which covers both launch markets. The anchor also makes every quote issued in the same half-day resolve to the identical instant, so the "trial dates have moved on" reload now only fires when the quoted date genuinely moved.
