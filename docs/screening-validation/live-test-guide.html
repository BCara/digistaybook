1 Open the consoles

Open screening logsOpen Firestore records

Sign in with the Google account that has access to the DigiStayBook project. Set Logs Explorer's time range to cover your test. The email address receiving warnings does not automatically grant console access.

2 Submit one identifiable test

  1. Open the correct guest link in a private browser window.
  2. Choose Add a memory, use a benign message such as “TEST 01 Lovely stay and a beautiful garden”, accept the draft consent and submit. For a photo test, use your own ordinary garden or room photo.
  3. Record the submission time, message label and whether the wall publishes it or says it is waiting.
  4. In Firestore, open guestSubmissions and locate your record using propertyId, createdAt and your test message. Read its screeningReference value.

The screening reference is an opaque 24-character identifier. Each edited revision has a different reference. Multiple retry attempts on the same revision share the reference; distinguish them by timestamp and the request trace where available.

3 Find all screening events

Paste this into Logs Explorer and run the query:

resource.type="cloud_run_revision"
jsonPayload.event=~"^screening_(text_result|photo_result|provider_decision|memory_decision|feedback_decision|final_state|error)$"

Expand a matching entry, then expand jsonPayload. Logs are written by the deployed Functions; the Google response is reduced to category names/scores or SafeSearch likelihoods. Raw message text, photos, credentials and provider response bodies are excluded.

4 Read Google's result and the app decision

EventWhat to inspect
screening_text_resultcategories: Google's category name and confidence from 0 to 1. durationMs and endpointRegion: au. A confidence value is not a measured accuracy rate.
screening_photo_resultOne entry per successfully scanned photo. photoIndex starts at zero; categories shows adult, spoof, medical, violence and racy likelihoods; endpointRegion: eu.
screening_provider_decisionPublic-memory provider outcome clear or standard, plus textFlagged/imageFlagged and the thresholds used.
screening_memory_decisionThe app's proposed memory outcome. contactDetailsOrLinkHold: true means Google cleared it but the app's local contact/link rule added review.
screening_final_stateThe stored memory status after publication checks. state_changed_no_publication means the submission/property changed and no publication was committed by that attempt.
screening_feedback_decisiondeliver or critical for private feedback. This is separate from public memory rules; feedback never appears on the wall.
screening_errorSanitised reason such as provider_http_403, provider_timeout, invalid_provider_response or daily_capacity_exhausted, and the resulting fallback. provider_or_storage_error is deliberately broad.

Current provisional memory settings hold any returned text category at confidence 0.8 or higher. Adult, medical, violence or racy photo classifications of LIKELY/VERY_LIKELY go to host review. Spoof is recorded but does not trigger that photo hold. These settings are still subject to calibration.

5 Confirm what actually happened

Firestore fieldMeaning
status: publishedThe memory passed the publication checks. Confirm it appears on the wall.
status: standardThe memory needs host review. Open the host review queue and approve or reject it.
status: pendingThe memory remains private awaiting screening. Check screening_error and screeningBudgetWaiting to distinguish failure from exhausted capacity.
feedbackStatus: delivered / heldPrivate feedback reached the host inbox or went to the restricted safety queue. Ordinary provider failure currently delivers feedback without a completed screen; this appears explicitly in the error event.
intakeMode: owner_authorised_testThis submission used the controlled test exception with draft legal wording.

A successful provider scan alone does not prove that the memory published, and a review hold does not necessarily mean Google flagged the content. Use the final record and wall together.

A short test sequence

  1. Benign text: check the category scores, decision and visible post.
  2. Benign text and one ordinary photo: check both providers and the photo index.
  3. A synthetic contact-detail example such as guest@example.com: distinguish the provider decision from the local review hold.
  4. Private complaint: check feedback delivery and confirm it never appears publicly.
  5. Edit your own memory, then delete it: inspect the new revision/reference and verify takedown.

Keep the test label, timestamp, screening reference, expected outcome and actual result. Use synthetic messages and authorised photos for the controlled test. The guide and diagnostic logs are not evidence of completed testing until you submit and inspect actual results.
