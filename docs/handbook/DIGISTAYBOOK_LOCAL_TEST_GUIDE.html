This guide opens directly from the NAS. Keep it open while testing. The test website links work once Test is running on the computer where you click them. Phone access is not configured.

1. Start local Test

Use the Windows computer with the DigiStayBook project and its development dependencies already installed.

  1. Open PowerShell or a terminal.
  2. Go to the project folder and start the local launcher:
    cd C:\Users\clbbe\Documents\Projects\DigiStayBook
npm run test:local
  3. Wait for TEST READY: http://127.0.0.1:5181/__test and for the website to start. Keep this terminal open while testing.
  4. Open the accounts and walkthrough page below, or use the links in this document.
Open local Test guide ↗Open sign-in ↗

The launcher starts the local website and Firebase emulators. It restores the last saved snapshot, or creates the original accounts and examples if no saved setup exists.

Already running? Use the links directly. A “port already in use” message usually means another session is using one of the required ports; see section 7.

4. Test steps

Use Test Cottage for this walkthrough. Keep the host browser open and use a separate private browser window for guest testing. Keep that guest window open to edit or delete the memories you create there.

  1. Check the host dashboard.Sign in as Host. Open Test Cottage and Draft Cottage.Expected: both original properties belong to this account. Existing saved changes may already be present.
  2. Edit the property.Change the Test Cottage welcome text or a host note. Save, then refresh the editor and guest page.Expected: the change persists and appears where that content is shown to guests.
  3. Check account settings.Open Account settings. Change the display name, save, and refresh. Restore the original name when finished.Expected: the name persists. Password/email changes and reset controls can also be exercised locally; any verification or reset link must be inspected through the local Auth tools or terminal output.
  4. Submit a clear memory.In the guest window, open the in-stay page. Add harmless text such as “A lovely test stay.” and an example photo. Accept the displayed consent and submit. Open the public wall.Expected: with host review off, the clear memory appears. With host review on, it waits for approval.
  5. Edit and delete your own memory.From the same guest session, edit the memory you just submitted and verify the change. Then delete it and refresh the wall.Expected: your edit persists and the deleted memory disappears. You can inspect its local deletion job and storage files in the data viewer; a queued job alone does not confirm file deletion.
  6. Check host approval.Turn host review on in Test Cottage. Submit another clear guest memory, then open Host review and approve it. Return the review switch to your preferred setting.Expected: the memory waits for approval and appears on the wall after approval.
  7. Try the screening examples.Submit harmless messages with the markers in section 5. Check Host review or Operations as appropriate.Expected: each contribution reaches the destination listed in the screening table.
  8. Submit private feedback.Use the guest page to send a harmless private suggestion. Sign in as Host and open Private feedback.Expected: clear feedback reaches the host and never appears on the public wall. Safety/outage examples remain in restricted review.
  9. Check host separation.Sign out, then sign in as Second host. Open the dashboard and try the Test Cottage editor link.Expected: the second host can manage Second Host Cottage, but cannot read or change the first host’s private records. The public wall remains public.
  10. Check Operations.Sign out and sign in as Operations reviewer. Open a safety case created in step 7. Inspect its reason and try the available release or deletion action on that local example.Expected: restricted cases appear in Operations. Any release follows the displayed workflow; unresolved cases cannot publish.
Seeded examples have a separate guest session. To test guest editing or deletion, create your own new contribution. You cannot use your guest session to edit the preloaded examples.

Record any failure with the step, account role, expected behaviour, actual behaviour and a screenshot. Shared results belong in the NAS Test Procedures results register. This guide provides instructions; it does not save results.

Check outage recovery

  1. Submit a memory containing [outage].
  2. Confirm that Operations shows its case tagged “Screening incomplete”.
  3. In the same guest session, edit your memory to remove the marker.
  4. Check that the open case still blocks publication until Operations releases it for renewed screening.

6. Save, stop and reset

Run these commands from the DigiStayBook project folder. For save, reset or worker commands, open a second terminal while the launcher keeps running.

ActionCommandWhat happens
Start or restartnpm run test:localStarts Test and restores saved data, or seeds the original examples.
Save nownpm run test:local:saveSaves local accounts, records and photos.
StopCtrl+C in the launcher terminalAttempts to save, then stops Test. Check the terminal for any save error.
Restore original examplesnpm run test:local:resetReplaces all local Test data with the original accounts and examples.
Run due background worknpm run test:local:workersRuns due screening retries and photo cleanup. Normal delays and backoff still apply.

The launcher saves and runs local workers every 30 seconds. It keeps three saved recovery snapshots in the project’s .local-test folder.

Reset replaces your local test work. Save any evidence you need first. After reset, sign out and back in. Start a new private guest window, or clear the test site’s browser data, for a fresh guest session.

After backend code changes, stop and restart the launcher so it rebuilds the local Functions.

7. If something fails

If Test closes unexpectedly, allow a few seconds for automatic process cleanup, then run npm run test:local again. It restores the last completed save. For an important test run, use npm run test:local:save before stopping; forcibly closing a terminal can interrupt the final save.

ProblemWhat to check
The website will not openConfirm the launcher is running, the terminal shows Test ready, and you are using http://127.0.0.1:5181 on the same computer.
“Port already in use”Use the existing Test session if it is yours. If restarting, stop your old launcher with Ctrl+C first. Required ports are 5181, 4400, 9099, 8080, 9199, 5001 and 4000.
Sign-in failsUse the exact example email and password. Check whether a password was changed in a saved test. After resetting, sign out and sign in again.
A seeded memory has no edit controlCreate a new memory from your own guest session; seeded contributions belong to a separate session.
A clear memory does not publishCheck the host review switch, the contribution’s status, and whether an open safety case is blocking it.
An email never arrivesLocal Test sends no real email. Inspect notificationOutbox in the local data viewer. Auth reset/verification links are local; check Auth tools or terminal output.
Cleanup has not runCheck its due time and status. The launcher runs workers periodically; the manual worker command does not skip production-style deadlines or backoff.
Startup or a save reports an errorKeep the exact terminal message and a screenshot. A ready website does not establish that a later save succeeded. Resolve the error before relying on that run’s saved data.

8. What local Test covers

Use local Test for host and guest journeys, account controls, ownership checks, review workflows, simulated screening and local data/photo handling.

Payments and real emails are disabled. Real Google classification, hosted App Check, real reviewer MFA, payment processing, inbox delivery and cloud deletion/recovery require separate live verification.

The test website runs on your computer using demo-digistaybook. The NAS stores this HTML guide; it does not run the test website.
